# 上下文预算与超限处理

本文记录当前 Workbench 配置及对应代码路径。预算值是工程上限。一次请求实际使用多少，取决于问题长度、所选证据、病例附件、是否展开父级及使用的模型分词器。配置上限也不等同于端到端吞吐量或质量评测结果。

## 一、各阶段的预算

| 阶段 | 当前配置 | 预算的含义 |
| --- | --- | --- |
| 知识库检索视图 | 最多 768 tokens | 用于索引和排序的单个视图。标题和章节路径等前缀也计入视图长度。原始文档、父级章节及表格附件单独关联保存。 |
| 检索结果与按需读取 | 每条 Query 重排后最多返回 5 个候选，每个子任务由选择器最多保留 2 条。普通检索上下文预算为 1,800 tokens。显式上下文读取预算为 4,096 tokens，父级窗口配置为 3 个关联 chunk。 | 候选数、上下文读取量和送入生成模型的证据数分别控制。父级原文和满足条件的表格行组可以在后续补充上下文。 |
| 共用问题整理、两路取证和证据审核 | Qwen3.5-4B。单次模型输入上限 8,192 tokens，默认输出上限 768 tokens，共同问题整理阶段输出上限 1,024 tokens。vLLM 配置两个序列槽，每槽 10,240 tokens。 | 两路可并发，单次请求分别核算输入与输出。具体任务可能使用更小的输出预算。 |
| 8B 初稿 | HuatuoGPT-3-8B。单次模型输入上限 20,480 tokens，输出上限 4,096 tokens，服务单槽 24,576 tokens。综合阶段的文献证据上限为 16,384 tokens、64 个来源。 | 先对完整请求计算总输入，再检查文献证据和来源数。初稿装包在总输入内额外预留 384 tokens。64 是装包上限，实际候选数量还受搜索、选择、复用和去重限制。 |
| 8B 终审的文献原文核对 | 同一 8B 角色。在总输入内预留 512 tokens。当前全池补缺阶段每批最多 6 个来源。 | 每批重新测量问题、答案清单、指令与原文的合计长度。条件冲突需要同批原文时，系统保留必要证据并独立判断能否同窗核对。 |
| 病例入口 | 获准病例文字、表格及附带问题合计上限 8,000 字符。 | 这是入口字符约束。后续仍按对应模型的分词结果核算 token，并保留病例来源、原文单元和表格关联。 |

排序视图和模型 Prompt 使用各自的分词器。模型侧会计入系统指令、原问题、历史视图、结构化状态、来源元数据、证据以及消息格式；底层还会校验输入与本次输出上限之和能否放进服务槽。检索侧的 768 tokens 因而只能用于说明排序视图的大小。

## 二、4B 如何处理候选和审核超限

1. **选择器读原文。** 同时放得下的候选一起比较。需要分装时保留候选原文，分批比较合格候选，再用能放进窗口的完整原文比较最后候选。选择结果按子问题记录。
2. **对已选原文做适用性核对。** 取证审核当前优先使用原文审核路径。每份来源按证据 ID 去重，每次提交一份选中原文与最多三个与之关联的任务。输出适用性、证据要点、原文锚点、限制和需要补读的局部条件。
3. **各路汇总核对回执。** 肿瘤与综合路使用原问题、自己负责的任务及对应原文回执，判断保留、证据缺口与定向补证。若单个完整原文审核或汇总请求无法适配 4B 窗口，显式记录未审核状态，原文和缺口留存。补检按限定预算执行，程序从重排后的 Top 5 中接纳最多两条合格的新原文，与首轮结果合并去重。

## 三、8B 初稿如何装入证据

**原文能完整放入。** 将去重且符合准入条件的全部入选证据原文、原问题和任务状态一起交给 8B。病例任务先确保完整的获准病例原文也能进入初稿，患者资料保留独立的来源定位。

**合并后超限。** 改按可回指原文的连续单元装包，优先纳入高优先级的完整条件组，再按与原问题的相关性和请求覆盖情况用其他原文填充余量。每个单元记录来源 ID、原文范围和是否交付。高优先级组之间也发生容量竞争时，逐组检查可容纳性，记录未入窗部分和原因。当前初稿链路在装包后生成一份初稿，分批核对原文发生在后续终审阶段。

**关键原文本身仍然超限。** 若高优先级证据组无法装入、原问题与基础状态本身超限，或者获准病例原文无法完整放入初稿窗口，系统报告对应的容量缺口。被暂缓的来源继续保存在后台。长咨询问题也可保留完整原文后向不同阶段装入已核验的原文单元，并记录待处理范围。

## 四、终审如何补到初稿未读的原文

1. **论断原文核对。** 4B 按初稿论断读取相应文献或病例原文，核对引用、适用条件和数字对应关系。可基于原文修正论断。核对超限或原文不可用时，将对应论断标记为待解决。
2. **8B 查遗漏和冲突。** 用原问题和完整答案清单对照获准的证据池，范围包含初稿未引用或装包时未读到的入选来源。每批尽量传完整原文。一份来源超过一批的容量时，可在可追溯且完整的原文单元边界分组。仍放不下的单元记为待核对。跨批出现互斥结论时，需要把对应的关键原文一起交给模型；联合窗口不足时保留冲突及其未解决状态。
3. **形成正式答案。** 针对新增或实质改写的论断做只读原文核验，再组织已支持的分析段落。相互独立且有据的内容可继续发布，剩余问题以证据缺口或容量缺口呈现。全池核对复用已有证据与定位，无需因此重新运行整条检索链路。

### 表格与图像

表格的表头、单位、脚注和相关行决定数据含义。结构已确认、依赖齐全且适配预算的表格行组才可形成检索视图或被装入模型上下文。父级读取可补充已确认的相关行与说明。终审中的合格表格单元按原子单元处理，单元超限或结构未确认时保留原件和未读原因。图像及图题保留来源位置，可作为后续查看的关联材料。

### 合成算量例子

假设两路各提交 3 个子问题，另有一条原问题兜底。一轮最多返回 7 × 5 = 35 个候选位置，选择器最多留下 7 × 2 = 14 个证据位置。同一原文被多个任务选中时，原文池只保存一份，并保留所有任务关联。

若去重后序列化的文献证据共 9,800 tokens，整份 8B 初稿输入实测为 14,200 tokens，计入 384 tokens 的预留后仍在预算内，可以使用完整原文。若父级补读后文献证据增至 17,000 tokens，即使总输入还有空间，也会触发原文单元装包，因为文献证据自身超过了 16,384 tokens。8B 终审能继续按批核对池内这些原文。这个例子只说明容量判断，候选数量、分词结果和审核质量要以各次运行记录为准。
